# 框架：挑选合适的 Agent 实现方式

进阶知识篇 · 依据参考侧栏主题补写

## 一、先看任务，再选框架

你要搭建的是客服问答、长流程执行，还是多个角色协作？先画出一次任务的输入、状态、工具和结果，再判断框架提供的能力是否值得引入。

![框架需要连接的三个层次](/agent-diagrams/07-architecture-1.png)

| 选择 | 更适合观察什么 | 动手前应检查 |
| --- | --- | --- |
| 自己写工具循环 | 模型调用、工具执行、终止条件 | 能否控制步骤与错误 |
| Coze 工作流 | 低代码节点编排与应用交互 | 输入输出绑定、发布与访问范围 |
| LangGraph | 有状态的长任务、暂停恢复和人工介入 | 状态结构、检查点、节点重试 |
| OpenManus | 通用任务执行器的组织方式 | 工具权限、运行环境、执行轨迹 |
| MetaGPT | 多角色协作和任务交接 | 角色产物、重复调用与结束标准 |
| Vanna | 面向数据库的自然语言查询 | Schema、授权范围和只读执行 |

## 二、用相同任务比较

::: tip 比较任务：查询订单并回答政策
输入一个订单号和售后问题；查实时订单；检索当前政策；输出带依据的答复。缺少字段时追问，工具超时后说明原因，涉及退款时转人工确认。
:::

不要在不同框架上使用不同难度的演示。固定同一组输入、模型、工具返回和验收标准，记录成功率、调用次数、总耗时和你维护代码的成本。

## 三、LangGraph：把状态画成图

它的核心是有状态的编排。一个节点做一件事，边规定下一步，状态保存跨步骤信息。人工确认是一个明确暂停点，恢复时继续使用已保存的状态。

```text
接收任务 → 查询订单 → 检索政策 → 生成建议 → 等待确认 → 执行 / 结束
             ↘ 超时：有限重试 → 失败说明
```

## 四、MetaGPT：把角色产物说清楚

参考侧栏出现了 MetaGPT 相关学习材料。学习多角色协作时，可以把流程拆成需求说明、方案、实现和检查。每个角色交付一个可检查产物，下一位读取该产物继续工作。

产品角色交付验收标准，研究角色交付来源与证据，实现角色交付程序与使用方法，检查角色交付可复现的问题。没有新证据的反复讨论要结束，而不是继续增加角色。

## 五、从框架抽象回到执行证据

框架简化代码，不会自动证明系统可靠。检查工具是否实际执行、状态是否恢复、重复写操作是否幂等、错误是否暴露给用户。用真实失败用例比较，比只统计示例代码行数更有意义。

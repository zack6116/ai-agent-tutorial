# 产品：Agents产品分析

产品视角 · 依据参考侧栏主题补写

## 一、用同一张任务卡看产品

分析 Agent 产品时，先问：谁在什么场景下，提供什么输入，希望拿到什么结果？再看产品怎样把模糊意图变成可检查的步骤，如何解释进度，以及失败后能否继续。

![从用户界面到业务逻辑的产品链路](/agent-diagrams/05-coze-app-1.png)

| 产品或项目 | 典型输入 | 可观察产物 | 分析重点 |
| --- | --- | --- | --- |
| Coze | 工作流需求和节点配置 | 可运行流程或应用 | 配置门槛、变量映射与调试 |
| OpenManus | 一句多步骤任务 | 工具执行后的结果 | 计划、权限与任务恢复 |
| FinRobot | 指定分析任务和数据范围 | 分析与报告 | 数据出处、计算口径与引用 |
| Vanna | 自然语言数据问题 | SQL和查询结果 | 表结构理解、授权与结果解释 |
| Lovart | 设计简报与品牌资料 | 设计素材与编辑结果 | 风格一致性、局部修改与交付 |

这张表按任务类型归纳，不是能力排名，也不代表各产品都适合你的数据与部署环境。

## 二、详解：Lovart.ai

Lovart 的官网将其描述为设计协作产品，覆盖从想法、生成到编辑的过程，并展示品牌资产与画布工作方式。这里把它作为“能交付视觉产物的 Agent 产品”分析。[官网](https://www.lovart.ai/)

::: tip 一个可复用的设计任务
为咖啡店的秋季活动准备三种尺寸的宣传素材。提供品牌颜色、准确文案、目标受众和尺寸；先确认构图与风格，再逐项修改，最后检查导出文件。
:::

**输入设计：** 让用户提供目标、素材和限制，减少反复猜测。**过程设计：** 把找参考、生成、修改等阶段显示出来。**结果设计：** 支持对具体元素提出修改，检查一处修改是否破坏其他已经确认的内容。

验收时看五件事：文字是否准确、品牌是否一致、主体是否完整、尺寸是否正确、文件是否可用。网页上“生成完成”的状态，不能替代这些检查。

## 三、把产品分析写成证据

| 观察项 | 记录方式 |
| --- | --- |
| 用户任务 | 保存真实需求的脱敏版本 |
| 关键路径 | 输入、启动、等待、修改、导出 |
| 用户控制 | 可以暂停、取消、撤回或确认什么 |
| 失败恢复 | 失败时保留了哪些输入与中间结果 |
| 价值 | 原任务耗时与完成质量如何变化 |

**练习：** 选择一个产品，完成同一个任务两次：一次按推荐路径，一次故意缺少一个关键输入。记录产品如何发现信息缺口、如何恢复。不要只收集宣传页上的功能名称。
